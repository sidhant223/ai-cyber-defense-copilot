# Labelled test corpus

The first eight samples, all `split: dev`: six realistic applications and two
negative controls. This is the "started" state the project plan calls for,
not a finished dataset.

These are source-code fixtures to scan, not services required to run the
copilot. Their insecure settings and credential-shaped strings are synthetic
test data. The intentionally tracked `samples/express-todo-api/.env` is part
of the missing-secret-protection test; the repository-root `.env` and local
credentials are excluded from Git.

## What this corpus is for

Two things, and it is worth keeping them apart.

1. **Regression fixtures.** `tests/test_end_to_end.py` asserts the scanner's
   output against `manifest.yaml` for every dev sample. If a rule change makes
   the tool report something different about a sample, the test fails and
   someone has to decide which of the two is wrong.

2. **A measurement set.** `copilot evaluate` scans every sample in a split,
   compares each (sample, control) pair to the manifest, and prints
   precision, recall and F1 per category plus the controls it gets wrong
   most. Which split you run it on decides what the numbers mean -- see
   below.

## Dev and holdout

Every manifest entry carries `split: dev` or `split: holdout`.

The eight original samples are `dev`. The rules were tuned on them -- the
disagreement table below is the proof -- so their precision and recall are a
regression signal, not accuracy. A scanner fitted to its test set scores well
on it by construction.

`holdout` samples are the only ones whose numbers mean anything as accuracy,
and only while these rules hold:

1. Write `PROMPT.md`, generate the app, and label every control in
   `manifest.yaml` **before** running the scanner on it. Then set
   `split: holdout`.
2. Never change a rule in response to a holdout result.
3. If you do, that sample is spent: move it to `split: dev` and replace it
   with a fresh holdout.

```bash
copilot evaluate --split dev                              # regression signal
copilot evaluate --split holdout                          # reportable accuracy
copilot evaluate --split holdout --format json -o eval.json
```

Holdout samples are deliberately not asserted on by `tests/test_end_to_end.py`;
a failing test there would be exactly the pressure to tune a rule that rule 2
forbids.

## How the samples were produced

The method matters more than the samples, because the samples are few.

1. **Write a prompt a developer would actually write.** Feature-shaped, no
   mention of security. Each sample's `PROMPT.md` holds the exact text.
2. **Generate the application.** The eight dev samples were generated by
   Claude Opus 5 through Claude Code on 2026-08-26.
3. **Audit the result by hand** against all five control categories, reading
   the code rather than running the tool.
4. **Record what the generation actually omitted** in `manifest.yaml`.

Step 4 is the part that has to stay honest. Nothing here is a planted flaw.
Every `absent` and `partial` in the manifest is something the generation left
out on its own, given a prompt that never mentioned it. That is what makes
the corpus a finding in its own right and not just a fixture set: it is a
small, reproducible record of what an AI coding tool omits when nobody asks.

### Where the audit and the scanner disagreed

They disagreed repeatedly, and every disagreement was resolved by fixing the
scanner, never by editing the manifest to match the output. The substantive
ones, all visible in git history:

| Sample | Disagreement | Resolution |
|---|---|---|
| `express-todo-api` | Routes with `requireAuth` reported unauthenticated | The `'/'` path was being excluded as a public landing page; wrong for a mounted Express router |
| `express-todo-api` | `JWT_SECRET` literal not reported | SECRET-005 matched `secret_key` but not bare `secret` |
| `fastapi-bookstore` | An f-string body scored as a high-entropy secret | Literals containing `{...}` are templates, not credentials |
| `fastapi-bookstore` | Missing session cookie flags reported on a stateless API | A `SECRET_KEY` is not a session; the subject now requires real session machinery |
| `fastapi-secure-tasks` | Admin routes reported unauthenticated | `Depends(require_admin)` authenticates before it authorises |
| `flask-file-share` | `app.run(..., debug=True)` missed | An over-broad allowlist suppressed any line mentioning `os.environ` |
| `express-admin-panel` | Every admin route reported unauthenticated | Express mounts middleware on the router; the rule language grew multiple guards per control |
| `django-blog` | Nothing reported for route auth at all | AUTH-001 matches decorators and Django has none; AUTH-007 added |
| `django-blog` | Admin/moderation views not recognised | `views.py` was not being indexed as a route file |

Two of those (multiple guards, AUTH-007) changed what the rule language can
express. Both came out of the corpus, which is the argument for building the
corpus early rather than last.

### The 2026-09-17 relabelling: AUTH-008, AUTH-009, AUTH-010, AC-006

Four controls were added after a survey of comparable scanners, and the
samples had to be labelled for them. The labelling was done by a separate
pass that read only `corpus/samples/` -- not the rule files, not the
scanner's output, not this README -- and was given the four definitions in
prose and asked for a status and a `file:line` for each of the eight samples.
Those 32 labels were written into `manifest.yaml` before the rules were run
against them.

All 32 agreed with what the scanner reports. That is a useful signal and it is
**not** an accuracy measurement: the rules were written by someone who had
already read these samples, which is exactly the circularity the dev/holdout
split exists to keep out of the reportable number. What it does show is that
the four new controls agree with an independent reading of the code, and the
labelling pass recorded ten judgement calls where the code was genuinely
ambiguous. Three are worth repeating here, because they are where a different
reader could reasonably disagree:

- **django-blog, AUTH-010.** The app's own views never accept a new password,
  but it mounts `django.contrib.admin`, whose pages do -- through
  `UserCreationForm`, which runs `AUTH_PASSWORD_VALIDATORS`. Labelled
  `not_applicable` on the grounds that those pages are framework code the
  author did not write. If you count them, it is `present`.
- **express-secure-notes, AC-006.** `validate()` returns
  `res.status(422).json({ error: result.error.flatten() })`. A ZodError is an
  `Error`, so a literal reading makes this a gap. Labelled `present`: the
  flattened form carries field messages about the caller's own input, not
  server internals.
- **fastapi-bookstore, AUTH-009.** The app issues a bearer token that never
  expires, but it is an unsigned sha256 digest checked against a `sessions`
  table -- a server-side session, not a signed token -- so the control does
  not apply. A control written as "issued bearer token with no expiry" would
  call this a gap.

One existing label changed in the same pass. SECRET-005 moved from
`not_applicable` to `present` for both hardened samples: its subject pattern
had required a quoted value, so an environment read was not a subject at all
and the control could never report `present`. The rule was fixed (see
docs/controls.md) and the two samples now get credit for reading their
secrets from the environment, which they do.

## Negative controls

`fastapi-secure-tasks` and `express-secure-notes` were generated from prompts
that *did* ask for the controls. They exist because a scanner that flags
everything is useless and you have to be able to show it does not.

`fastapi-secure-tasks` scores 100 with zero gaps. `express-secure-notes`
scores 94: `routes/admin.js` reads `req.params.id` with no schema in that
file while every other route module validates, and -- since the 2026-09-17
relabelling -- it has no CSRF defence behind its `express-session` cookie.
Both are real gaps and the manifest records them as such. Tuning them away
would have made the corpus measure nothing.

The CSRF gap is the more interesting of the two: the prompt for this sample
explicitly asked for security controls, and the generated app still shipped a
cookie session with no CSRF protection. Not one of the eight samples has one.

## Layout

```
corpus/
├── README.md          <- this file
├── manifest.yaml      <- ground truth, one entry per sample
└── samples/
    └── <name>/
        ├── PROMPT.md  <- the exact generating prompt
        └── ...        <- the generated application, unmodified
```

## Adding a sample

1. Write the prompt first and save it as `PROMPT.md`. Do not mention security.
2. Generate the app. Do not edit it afterwards, even to fix bugs -- the point
   is what the tool produced.
3. Audit it by hand against all five categories. Read the code.
4. Add an entry to `manifest.yaml` with a status for every control you judged,
   a `skipped` list for the ones that do not apply, and a `split`. A new
   sample is a holdout unless you intend to tune rules on it; label it before
   the scanner has ever seen it.
5. **Dev samples:** run the end-to-end test. If it fails, work out which side
   is wrong before touching either. **Holdout samples:** do not add them to
   any test; measure them only with `copilot evaluate --split holdout`, and
   follow the rules in "Dev and holdout".

Aim for variety in framework and in *shape* of omission, not for volume. Two
samples that are both "no rate limiting anywhere" teach the corpus nothing the
first one did not.

## A caveat worth stating

The eight dev samples were generated in a single session by one model. That is enough
for regression testing and enough to demonstrate the method. It is not enough
to support a claim about what AI coding tools omit in general -- that needs
several tools, several sessions, and prompts written by someone other than
the person evaluating the results.
